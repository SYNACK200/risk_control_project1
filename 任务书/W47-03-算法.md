## 二、目标：一个入口

```python
# rc_platform/capabilities/parse/entry.py（新）
def parse_statement(*, data: bytes | None = None, rows: list[dict] | None = None,
                    profile: dict | None = None) -> Statement:
    """全项目唯一的解析入口：PDF 字节或已解析 rows，都从这里出 Statement。"""
```

- 内部择路：有 rows 直接转；有 data 先 `layout_v2`，若日期覆盖率 < 50% 再用 `algorithm.ocr.parse` 兜底
- **兜底逻辑从 Lab 移到这里**，Lab、业务后端、CLI 都调这一个函数
- 选择结果写进 `Statement.meta`（`parser_used` / `dated_ratio`），便于复盘「为什么这次用了兜底」

## 三、任务卡

### AL-101 · 统一解析入口（P0，1.5 天）
- 新建 `rc_platform/capabilities/parse/entry.py`，实现上面的 `parse_statement`
- 把 Lab 的 `_statement_from_bytes` 改为调用它（删掉那份兜底代码）
- `Statement.meta` 加 `parser_used`（`layout_v2` / `legacy_fallback`）、`dated_ratio`、`row_count`
- 验收：同一份建行件，从 Lab、业务后端、CLI 三个入口调用，`row_count` 与 `dated_ratio` 完全一致

### AL-102 · 特征与指标的映射表（P0，0.5 天）
- 产出 `docs/特征指标映射.md`：40 项指标 × 「能否用现有特征表达」
  - ✅ 已覆盖（例：A01 期间收入合计 ↔ `f_in_total`）
  - ⚠️ 口径不同（写出差异：例如指标剔除六类同名互转，特征没剔）
  - ❌ 缺特征（列出需要补的特征名与表达式）
- 验收：40 行全有结论，不许留「待定」

### AL-103 · 金标样本集（P0，1 天）
- `algorithm/inputs/golden/`：建行 / 广发 / 招行 三份（已脱敏），每份配 `expected.json`
- `expected.json` 内容：`row_count`、`dated_ratio`、以及 12 个关键特征的期望值（字符串，DECIMAL 口径）
- 期望值必须**手工核算过**（用 Excel 或 SQL 复算一遍），不许「跑一遍记下来」
- 验收：`pytest algorithm -q` 里新增一组金标回归，全绿

### AL-104 · 特征口径校验（P0，1 天）
- 从 46 个特征里挑 8 个高价值的做手工核算对照：`f_in_total`、`f_in_cv`、`f_month_in_cv`、
  `f_large_out_share`、`f_counterparty_hhi`、`f_month_end_balance_slope`、`f_overdraft_days`、`f_recent30_flow_ratio`
- 每一条给出：表达式、样本、期望值、实测值、差异原因（若有）
- 验收：`docs/特征口径核算.md` 8 条全对；对不上的要么改实现、要么改口径说明

### AL-105 · 不可算原因标准化（P1，0.5 天）
- 原因字典（就这几类，不许自由发挥）：
  `missing_column`（缺列）/ `no_rows`（该口径下无数据）/ `no_denominator`（分母为 0）/
  `insufficient_period`（期数不足）/ `invalid_input`（输入不合法）
- 特征定义里 `reason` 一律返回 `{"code": ..., "message": "中文一句话"}`
- 验收：46 个特征在同一份缺 `trade_time` 的件上，原因码全部落在字典内

### AL-106 · 边界与性能（P1，0.5 天）
- 20000 行的计算耗时与内存上限；单特征 > 200ms 的要标出来
- 边界：0 行、1 行、全空列、amount 为负、balance 缺失
- 验收：`docs/特征性能.md` 给一张表（行数 × 耗时），超过 200ms 的列出原因
