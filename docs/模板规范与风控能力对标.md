# 模板规范与风控能力对标（2026-11）

> 目的：回答两个问题——① 我们的模板标注方式为什么鲁棒性低、业界怎么规定；② 风控部分相比成熟产品缺什么。
> 结论均标注来源，凡属推断的都写明「推断」。

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| 模板为什么脆弱 | **我们让用户手画列矩形**，边界靠人眼；业界一律**以表头文字为锚、由系统算列边界**。人手画 → 每个人的框差几个像素 → 同版式出现多个模板 → 失效 |
| 风控为什么粗糙 | 我们有 40 个指标和 5 级真实性判断，但缺**交易分类（categorisation）**这一层；业界所有「收入核实/负债识别/风险标签」都建立在分类之上 |
| 最该先做的一件事 | **把「画列框」换成「点表头定列」**——这是消除口径差异、提升鲁棒性的根，不是优化项 |

## 1. 外部对标：模板/解析侧

### 1.1 业界共识（多源一致）

| 要点 | 出处 |
|---|---|
| 银行流水 PDF 没有结构性表格，只有 x/y 上的词；列必须从词坐标重建 | [Rebuilding table columns from word coordinates](https://statementxl.hashnode.dev/rebuilding-table-columns-from-word-coordinates-in-bank-statement-pdfs)、[statementsheet](https://statementsheet.com/technical-guides-articles/how-to-detect-transaction-tables-in-pdfs/) |
| 模板解析器 = 针对某一家银行版式写的一组规则，「每条规则说某个值在哪里」，不是一堆矩形 | [Schema CPA: Templates, Rules and Layouts](https://schemacpa.com/blog/bank-statement-parser) |
| 表格跨页、每页重复表头；把页当独立对象会把重复表头读成数据行 | [pdfmux: Extract data from bank statements](https://pdfmux.com/blog/extract-bank-statement-data-python/) |
| extract_table() 类库在流水上「失望多于惊喜」，实用起点是 words + coordinates | [FlowParse: Bank Statement Parser in Python](https://flowparse.io/bank-statement-parser-python) |
| **余额链复核是标配**，且「多数教程跳过这一步」——漏一行会让总额静默错掉 | [pdfmux](https://pdfmux.com/blog/extract-bank-statement-data-python/) |
| 解析器会因银行改版失效，所以要模板版本 + 失效检测 | [Schema CPA](https://schemacpa.com/blog/bank-statement-parser)、[bankstatementlab](https://www.bankstatementlab.com/en/blog/en-bank-statement-pdf-format-varies-parsing-fails) |

### 1.2 我们现在的做法 vs 业界

| 环节 | 我们 | 业界 | 判定 |
|---|---|---|---|
| 锚点 | 表头别名（apply_template）已在用 | 表头文字为锚 | 一致 |
| 列边界 | **用户手画矩形** | 系统按表头词中点/间隙算 | **差异根源** |
| 表格区 | 用户手画外框 | 由表头行 + 最后一个数据行推导 | 多余自由量 |
| 表头高度 | 用户填 0–1 小数 | 自动检测表头行（我们有 detect_header_row，但标注时不用） | 已有能力未用 |
| 跨页 | 支持（page 字段） | 表头每页重复 | 需验证重复表头不误当数据 |
| 余额链 | 已做 | 标配 | 一致 |
| 版本 | v1/v2/v3 | 模板版本 + 失效告警 | 基本一致 |

### 1.3 鲁棒性为什么低（根因拆解）

当前一个模板由这些自由量组成：表格区矩形 (x,y,w,h) + 每列矩形 (x,w) + 表头高度 + 银行代码 + 表头关键词。
**自由量越多，「同一份文件、两个人标注」的差异越大**：

1. 列边界：有人画在表头字中间，有人画到两列间隙——两者都能过校验，但落在不同列
2. 表格区：有人包住表头，有人从第一条数据开始——影响 headerY 推导
3. 表头高度：留空则取 area.y + 0.01，可能落在空白行，后端取不到表头词
4. 结果：**同一银行出现多个「模板」**，每个只对某个人的画法有效

这解释了为什么现状下「模板建得出来、但换一份文件就失效」。

## 2. 模板标注口径规范（建议，可执行）

> 目标：让「任何一个人来标，产出的模板都等价」。做法不是写文档约束人，而是**把自由量从人手里拿走**。

### 2.1 硬规则（系统强制，不靠人遵守）

| # | 规则 | 实现方式 |
|---|---|---|
| R1 | **列边界不由人手画**，由系统按表头词 x 区间自动生成：列左界 = 表头词左边 − 0.2×词宽，右界 = 下一个表头词左界 | 前端「点表头定列」 |
| R2 | 列不可重叠；相邻列之间必须留空（由 R1 自动保证） | 自动 |
| R3 | 表格区 = 表头行上沿 到 本页最后一个含金额的行下沿 | 自动推导，用户不画 |
| R4 | 表头高度 = 表头行下沿（detect_header_row 的结果） | 直接取检测值 |
| R5 | 序号/流水号列不参与字段映射，但保留在模板里（用于行序校验） | 自动标 excluded |
| R6 | 模板记录 layout_hash（表头词序列哈希）；新文件哈希不匹配时不直接用模板，先跑表头比对 | 新增字段 |
| R7 | 每列记录 header_text（当时表头词原文），解析时以它为唯一锚点 | 补列级记录 |

### 2.2 用户实际要做的事（三步，且都是「点」不是「画」）

1. 点一下表头行里的第一个词（系统据此定位整行）
2. 给识别出的列勾选字段（系统已按表头名预填建议）
3. 确认

> 现在的「画表格区 / 画列边界 / 调表头高度」三个动作全部消失。

### 2.3 与现有实现的兼容

- field_map 语义不变（表头 aliases / 列号）——已有模板继续可用
- 新增列级 header_text 与模板级 layout_hash，老模板为空时回落到当前行为

## 3. 外部对标：风控侧

### 3.1 业界流水分析的标准动作（多源一致）

| 层 | 内容 | 出处 |
|---|---|---|
| 1. Ingestion | 抽取交易、余额、账户元信息，处理数百种版式 | [Befisc](https://www.befisc.com/fintechsherlock/bank-statement-analysis-for-lending/) |
| 2. **Integrity checks** | 运行余额 = 前余额 + 贷 − 借；字体/元数据/版式是否匹配发卡行已知模板；**日期是否有缺口** | 同上 |
| 3. **Categorisation** | 每笔打标签：salary / business receipts / EMI / rent / cash deposit / self-transfer / **gambling / crypto** / 退货 | 同上 |
| 4. Metrics | 核实收入、平均最低余额、固定支出（房租/还款/订阅）、风险标签 | [FlowParse](https://flowparse.io/bank-statement-analysis-for-loans) |
| 5. 决策 | 把干净数据喂给 affordability 模型 / scorecard | 同上 |

### 3.2 成熟产品宣称能算的东西

- **80+ 预测变量**（把原始流水变成变量集）：[Periculum](https://www.periculum.io/post/how-bank-statement-analysis-is-transforming-digital-lending-in-africa)
- **4 层 pipeline**（OCR → 交易抽取 → 分类 → 分析）：[AZAPI](https://azapi.ai/blog/bank-statement-analyzer-api-for-loan-underwriting/)
- **cash-flow underwriting**（把交易变成 affordability 信号）：[Rexto](https://rexto.com/cash-flow-underwriting)

### 3.3 我们 vs 业界（风控）

| 能力 | 我们 | 业界 | 差距 |
|---|---|---|---|
| 交易抽取 | 40 指标 + 36 校验点 | 同 | 基本一致 |
| 余额链复核 | 有 | 有 | 一致 |
| 真实性五级 | pass/grant/supplement/fail/unknown | 分法不同，目标一致 | 有特色 |
| **交易分类（categorisation）** | **只有关键词命中，没有逐笔归类** | 核心层 | **最大缺口** |
| 收入核实 | 靠「工资关键词」 | 跳跃检测（跳增/跳减/规律性） | 粗糙 |
| 负债/还款识别 | 部分（贷款平台数） | 逐笔 EMI、订阅 | 粗糙 |
| 日期缺口检测 | 无 | integrity check 标配 | **缺口** |
| 低置信度字段标记 | 只有文件级 warnings | 字段级 confidence | 缺口 |
| 多账户/多月份合并去重 | 无 | Smart Merge | 缺口 |
| 变量集 | 40 个固定指标 | 可配置变量（80+） | 差距在「可配置」 |

## 4. 风控功能建议（按性价比排序）

### P0（不做则结论不可信）

| # | 功能 | 为什么 | 工作量 |
|---|---|---|---|
| F1 | **逐笔交易分类**（salary/transfer/loan_repay/cash/gambling/crypto/merchant…） | 所有高级指标的地基；现在「工资收入」靠关键词硬匹配，漏一个就低估收入 | 中 |
| F2 | **日期缺口与跳号检测** | 业界 integrity check 标配；借款人常删掉不利月份 | 小 |
| F3 | **字段级置信度**（每笔每字段 0–1，低置信度进报告） | 现在只有文件级 warnings，无法定位「哪笔有问题」 | 中 |

### P1（决定体验与说服力）

| # | 功能 | 为什么 |
|---|---|---|
| F4 | 收入核实升级：工资规律性检测（同额同日期每月出现 → 高置信；金额乱跳 → 低置信） | FlowParse 的 Verified income 就是这个 |
| F5 | 负债画像：逐笔 EMI/还款识别 + 月度固定支出 | 现在只有「贷款平台数」 |
| F6 | 多账户/多月份合并去重 | 避免同一笔转账重复计入收入 |
| F7 | 变量集可配置（40 个固定指标 → 指标库 + 启用开关） | 不同银行风控口径不同 |

### P2

| # | 功能 | 为什么 |
|---|---|---|
| F8 | 版本化评分卡（权重可调 + 版本对比） | 现在分数是固定规则 |
| F9 | 反欺诈图谱（同一对手方在多个申请人之间出现） | 团伙欺诈识别 |
| F10 | 数据导出（干净 CSV/JSON 给客户的风控模型） | 银行侧常在自有模型里二次使用 |

## 5. 建议的实施顺序

1. **先做 R1–R5（点表头定列）**：这是模板鲁棒性的根，能立刻消除「不同人画法不同」
2. **再做 F1 + F2**：分类 + 日期缺口，把风控从「关键词命中」提升到「逐笔归类」
3. 然后 F3（字段级置信度），它依赖 F1 的分类结果做校验
4. R6/R7（layout_hash + header_text）与 F1 并行做，成本低

## 6. 未验证 / 风险

- 未验证：跨页重复表头是否会被误读成数据行（需用 12 页样本专门测）
- 未验证：图片件在透视校正缺失下的分类准确率（无基准数据）
- 风险：点表头定列依赖 OCR 正确识别表头；表头识别失败时需保留「手动兜底」入口
- 风险：业界结论来自英文产品页与博客，**未做同行业样本实测**，只能作为方向参考
