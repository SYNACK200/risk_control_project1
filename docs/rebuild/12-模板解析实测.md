# 模板解析能不能跑：实测记录

> 2026-11-14 · 分支 `rebuild/v1` · 结论先行：**能跑，而且模板真的在起作用；模板错了会被核验层抓到。**

## 一、怎么证明「模板真的在用」

不靠读代码，靠**扰动实验**：把 CCB 模板（#26 v3）里「收入金额」和「余额」两列的列带位置对调，
重新上传同一份文件，看解析结果跟不跟着变。

| 任务 | 用的模板 | 第 1 笔 amount | 第 1 笔 balance |
| --- | --- | --- | --- |
| #155 | #26 v3（正常） | 12500.00 | 13200.00 |
| #156 | #27 v4（两列对调） | **13200.00** | **12500.00** |

结果跟着模板变了，数据库里也记着 `task.template_id=27, template_version=4`。
如果模板只是摆设，这两份任务会给出完全一样的数字。

## 二、模板错了会怎样（这条更重要）

#156 的结论是 `存在不一致`，理由：「内容层核对失败（数据断）：第 1 页合计不符：收入 印 25000.00 实 107047」。

也就是说模板读错时，合计对不上会被抓住，不会静默出一份「看起来正常」的报告。
这是内容层自校验在兜底——模板可以错，但不能错得没人知道。

顺带暴露一个规律：**方向是跟着列来的**。#156 因为把余额列当成了收入金额列，全部交易被判成 `in`；
金额列一错，方向、收入、DTI 会连锁错。所以模板调错时，别只看「有没有报错」，要看合计。

## 三、链路现状

| 环节 | 现状 |
| --- | --- |
| 模板数据模型 | `layout.tables[].columns[]` 列带（归一化 x/w）+ `field_map` + `headerY`/`area`/`slot` |
| 保存 | 标注画布保存为草稿；改一次生成新版本（v3 → v4），旧版本进历史不覆盖 |
| 启用 | `publish` 后参与解析；同一银行同时只有一个 `enabled` |
| 解析 | **老链路**：`backend/services/analysis.py` 把模板转成 `ParseTemplate(field_map, layout)` 交给 `algorithm.parse` |
| 新平台 | `rc_platform/capabilities/parse/plugin.py` 支持从配置注入模板（`parse.template`），但**还没有从数据库读模板**，目前线上走的是老链路 |

## 四、还没做到的

1. **新平台没接模板库**：`rc_platform` 的 `parse.algorithm_compat` 能从 setting 读模板，但没人把
   `template` 表里的启用模板喂给它；现在两条链路一份模板、两种取法，切换时必须先补这一层。
2. **模板没有「必需列」声明**：缺列不会在模板层报错，要到指标层变成「不可算」。
3. **一页多个表格区只取第一个** `tables[0]`。
4. **没有档期/账户类型过滤**：只按 bank_code 命中，同银行不同版式（换版）会互相踩。
