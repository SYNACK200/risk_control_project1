## 状态机

```
                 enqueue
                    │
                    ▼
                ┌────────┐  claim（原子，attempts+1）  ┌─────────┐
                │ queued │ ────────────────────────────> │ running │
                └────────┘ <──────────────────────────── └─────────┘
                  │   ▲        fail(retryable, 还有次数)       │
                  │   │        next_run_at = now + backoff      │
                  │   └────────────────────────────────────────┤
                  │                                            │
        cancel    │                    complete ───────────────┤──> done
                  ├────────────────────────────────────────────┤
                  ▼                                            │
             ┌───────────┐   fail(retryable=False) ────────────┴──> failed
             │ cancelled │
             └───────────┘        fail(次数耗尽) ─────────────────> dead
                                  reclaim_expired(次数耗尽) ─────> dead
```

| 状态 | 含义 | 谁写 |
| --- | --- | --- |
| `queued` | 排队中；`next_run_at` 未到的（退避中）也在这里 | enqueue / fail(可重试) / reclaim |
| `running` | 被某个 worker 持有，持有凭据是 `lease_until` | claim |
| `done` | 正常完成 | complete |
| `failed` | 不可重试的失败（数据本身错了，再跑还是错），终态 | fail(retryable=False) |
| `cancelled` | 人工取消（排队中与运行中都能取消），终态 | cancel |
| `dead` | 重试次数耗尽，终态；最后一次错误留在 `error` 上给人工排查 | fail / reclaim_expired |

「运行中被取消」靠租约而非杀线程实现：worker 每次 emit 都会续租，续租失败（任务已不归它）
就知道该停手；迟到的 `complete` 因为带期望条件 `status=running`，写不进去，返回 `None`。

## 重试策略

```
第 n 次尝试失败后的等待 = min(cap, base * 2^(n-1))    base = 2s，cap = 300s
```

| 已尝试次数 | 1 | 2 | 3 | 4 | 5 | ... | >=9 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 等待（秒） | 2 | 4 | 8 | 16 | 32 | ... | 300（封顶） |

- `attempts` 在 `claim` 时加一，所以「跑过几次」永远等于库里的 `attempts`，不靠外部计数。
- `attempts < max_attempts` 且 `retryable=True` → 回 `queued` 并设 `next_run_at`；
  `attempts >= max_attempts` → `dead`；`retryable=False` → 直接 `failed`。
- 默认 `max_attempts=3`（入队时可改），即最多执行 3 次。
- 退避期间任务留在 `queued`，`claim` 用 `next_run_at <= now` 过滤，不会被提前领走。

## 租约与心跳

```
worker                     QueueService                     store
  │ claim(worker, 60s) ───────>│  status=running, attempts+1, lease_until=now+60s
  │                           │──────────────────────────────> 条件 UPDATE（rowcount=1 才算领到）
  │ emit(ProgressEvent) ──────>│  stage/progress 落库
  │ heartbeat ────────────────>│  heartbeat_at=now, lease_until=now+60s
  │ ...                       │
  │ complete ─────────────────>│  status=done, finished_at, progress=1.0
```

- 租约时长默认 60s，`claim` 可传 `lease_seconds`；每次 `heartbeat` 从「现在」重新计，不累加。
- worker 每上报一次进度就续租一次（`worker.py` 的 emit 同时做 `record_progress` 与
  `heartbeat`）：长任务靠这条路径保命，不必另开心跳线程。
- `reclaim_expired()` 扫 `running` 且 `lease_until <= now` 的任务，按「这次尝试失败」处理，
  复用同一套重试策略：还有次数就排队重试，次数用完了进 `dead`。返回回收条数。
- 进程崩溃不需要特殊处理：租约到期后由下一次 `reclaim_expired` 收走。

## 银行侧队列页需要读哪些字段

页面按 `GET /queue/jobs?status=&page=` 展示列表、按 `GET /queue/stats` 展示顶部卡片。
一条任务行只需要这些字段（`Job.to_dict()` 就是给这个用的）：

| 字段 | 队列页怎么用 |
| --- | --- |
| `id` | 详情页/日志的锚点 |
| `biz_no` | 「哪张单子」——业务编号，银行侧最常用来搜 |
| `status` | 行上的状态标签；六个取值与中文对照见下表 |
| `priority` | 排序说明（为什么这张排在前面） |
| `attempts` / `max_attempts` | 「第 2/3 次尝试」 |
| `stage` | 当前阶段（能力名，如 `parse.layout_v2`） |
| `progress` | 0~1 的比例，页面乘 100 画进度条 |
| `payload` | 详情抽屉里的原始入参 |
| `error` | 失败原因；`dead` 行必须展示，供人工重放 |
| `worker_id` | 运行中显示「在哪台机器上跑」 |
| `enqueued_at` / `started_at` / `finished_at` | 入队/开始/结束时间，用于算等待与耗时 |
| `heartbeat_at` / `lease_until` | 运行中显示「最后一次心跳」；超过 `lease_until` 说明 worker 已失联 |
| `next_run_at` | 退避中显示「下次重试时间」 |

顶部卡片读 `stats()`：

```python
{
  "total": 12,              # 全部任务数
  "queued": 4, "running": 1, "done": 5, "failed": 1, "cancelled": 1, "dead": 0,
  "oldest_enqueued_at": "2026-11-09T08:00:00+00:00",  # 最早入队时间（积压多久）
  "running_workers": 1,     # 正在运行的 worker 数（按 worker_id 去重）
  "avg_wait_seconds": 2.35, # 平均等待：started_at - enqueued_at
}
```

另有 `position(job_id)`：排队名次（1 起，退避中的任务也占位），运行中/已结束返回 `None`。

状态中文对照（前端别自己拼）：`queued` 排队中 · `running` 执行中 · `done` 已完成 ·
`failed` 失败（不可重试） · `cancelled` 已取消 · `dead` 已死信（次数耗尽）。

## 已知限制

1. `stats()` 全量扫描：万级以内够用，量大应下推成 SQL 聚合（接口形状不变）。
2. `run_loop` 不含信号处理与优雅停机：常驻进程由调用方管线程；`idle_limit` 只给测试与
   一次性批处理收尾。
3. `SqlAlchemyStore` 进程内加锁是为 sqlite 内存库共用单连接（StaticPool）准备的；MySQL 下
   属于多余的本地串行，跨进程正确性仍由条件 UPDATE 保证。
4. 不存执行产物（`payload` 是输入），也不做延迟任务与定时任务。
