# M4 交付记录（上）：核验层插拔化

> 日期 2026-11-10 · 分支 `rebuild/v1` · 上一阶段：M3

## 这一阶段把「核验」拆成了四个可拔插的层

| 能力 | 契约 | 依赖 | 说明 |
| --- | --- | --- | --- |
| `verify.file_layer` | layer_file | document, profile | 载体层：生成器/增量/字体/隐藏文字/覆盖图元 |
| `verify.content_layer` | layer_content | statement | 内容层：C1–C10 与一票否决 |
| `verify.ledger_layer` | layer_ledger | statement | 账务层：借贷平衡/结息/期末余额 |
| `verify.external_layer` | layer_external | statement | 外部层：默认全占位，只报未启用 |
| `verify.compose` | verification | 前四层（账务/外部为可选） | 只做五态合成，判据一行不抄 |

三条设计决定：

1. **判据不搬家**：五态规则、一票否决的成因区分仍在原处，compose 只调用不重写。
   抄一遍判据 = 又开一套口径，这是重构里最容易犯又最难发现的错。
2. **层可选**：`optional_requires` 让「本行没接入外部层」成为正常状态，而不是装配失败。
   缺层时结论照出，layers 里该层为 `skipped`，限制说明照写。
3. **层可换**：同名契约允许两个实现，`overrides` 指定即换，主干不动一行。

# M4 下半程（上）：指标与特征的映射表

## 为什么先做表不直接换实现

「指标一套、特征一套」的风险不是抽象的：同一个概念两个实现，改口径要改两处，
漏一处没有任何东西会报错。所以第一步不是改代码，是把 40 项指标逐个登记成
「可映射（表达式）」或「卡在哪（具体原因）」，然后用命令逐值对照。

## 交付

| 交付物 | 路径 | 作用 |

# M4 下半程（下）：补齐三类算子，映射从 7 项推进到 19 项

## 补齐的算子（8 个，注册进全局算子库，表达式里可直接用）

| 算子 | 语义 | 为什么必须单独做 |
| --- | --- | --- |
| `coverage_months(min_months=1)` | 覆盖自然月数（整月计 1，首末按当月天数折算） | 不足一个月按一个月计——4 天的流水按 4/31 折算会把月均收入放大 7 倍 |
| `month_count()` | 覆盖期间跨了几个自然月（含空月） | 与 `coverage_months` 不是一回事：A04/D01 的守卫用的是「月数 ≥ 2」，不是「折算月 ≥ 2」 |
| `monthly_values(agg=sum\|count)` | 逐月值，空月补 0 | 不补 0 就没有「休眠月」也没有中位数 |
| `daily_balances()` | 日终余额序列（无交易日结转） | 余额波动率的分母是日终序列，不是原始逐笔余额 |
| `pstdev()` | 总体标准差 | features 里的 `std` 是样本标准差，两者差一个 n/(n-1) |
| `slope()` | 序列的最小二乘斜率 | 收入趋势、期末余额趋势都靠它 |
| `month_end_balances()` | 各月最后一天的日终余额 | 期末余额趋势的输入 |
| `share_square_sum()` / `top_share(k)` | 按对手方汇总后求占比平方和 / 前 k 占比 | HHI 要「分组 → 占比 → 再聚合」，单靠现有聚合算子拼不出来 |

## 一路上踩到的三个口径坑（都是对照抓出来的）

问题：`coverage_months` 一开始按真实折算返回 0.129，微信那份 4 天的流水月均收入算成 2232.56，旧实现是 288.00。解决状态：已修——旧口径把不足一个月按一个月计（`max(1.0, exact)`），算子加了 `min_months=1` 下限并写进测试。事后反馈：这类「看起来更精确其实更错」的口径最容易在重写时被引入，而且不会有任何报错；对照不跑到有样本的边界上就发现不了。

问题：A04 与 D01 的守卫条件，我按「折算月数 < 2」写，旧实现按「自然月个数 < 2」写。解决状态：已修——新增 `month_count()` 专管这个，两者语义分开命名。事后反馈：同一句话「覆盖月不足两个月」在两种度量下不是一回事（1.084 个月 vs 2 个自然月），命名不分开，后面一定还会有人踩。

问题：C04 的 0.3061 对不上任何「逐笔余额标准差」。解决状态：已修——旧实现算的是**日终余额序列**的总体标准差除均值，不是逐笔余额。事后反馈：这说明「口径」不只是公式，还包括取哪份数据；只看代码名字（余额波动率）根本推不出来，必须读实现。
