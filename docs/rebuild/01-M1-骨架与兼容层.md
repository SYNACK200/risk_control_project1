## 这一阶段交付了什么

| 交付物 | 路径 | 作用 |
| --- | --- | --- |

## 验收证据（实跑）

```
python -m pytest rc_platform/tests -q
17 passed in 2.70s

python -m rc_platform.cli algorithm/inputs/samples/synthetic/clean/icbc.pdf -v
[1/5] preread.algorithm_compat ok
[2/5] parse.algorithm_compat   ok
[3/5] verify.algorithm_compat  ok
[4/5] metrics.algorithm_compat ok
[5/5] report.algorithm_compat  ok
结论：未发现异常（已完成的核验未发现矛盾；部分检查不可算）
明细：6 笔 · 指标 40 项 · 用时 2601ms
```

对照断言（`tests/test_parity_compat.py`）：

- 新骨架的 `verification.verdict` == 封存版 `backend/services/analysis.run_analysis` 的 `report.verdict`
- 新骨架 `statement.rows` 笔数 == 旧版 `txn_count`
- 40 项指标的 `code → value` 全等

**结论：容器换了，判据没换。** 这是 M1 唯一要证明的事。

## 三条已经生效的架构约束

1. 主干不 import 任何具体能力——有测试（`test_core_never_imports_concrete_capabilities`）扫 `core/` 的 AST，违反即失败。
2. 能力只通过 `contracts.py` 交换数据；契约名未登记时注册即报错。
3. `document` 是外部输入契约，装配时视为已满足；其余契约必须有能力产出。

## 已知限制

- 兼容能力把旧对象塞在契约的 `native` 字段里传递，这是**过渡期**的合法逃逸口；
  M2/M3 的新实现必须自己填契约字段，`native` 只允许出现在 `.algorithm_compat` 这一类能力上。
- 契约 `Statement.rows` 目前由旧 `ParseResult` 逐字段搬过来，尚未承担「列带/证据坐标」等新字段。
- 新平台没有 HTTP 层，所以「服务能起」这一条本阶段由封存版服务承担；M4 起换成新 API。
