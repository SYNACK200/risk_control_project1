## 二、访谈结论（三轮，10 个决策）

| # | 问题 | 选定 |
| --- | --- | --- |
| 1 | Lab 形态 | 独立进程 + 独立端口，同仓独立包 |
| 2 | 反馈语义 | 提交 → run_id + 指标清单 → 按 run_id 取数值 |
| 3 | 输入边界 | 结构化流水 JSON 为主，PDF 可选 |
| 4 | 本周范围 | 前端信息架构全量重组也纳入本周 |

| 7 | 鉴权 | 服务间 API Key（`X-Api-Key`） |
| 8 | 任务书 | 四份：前端 / 后端（含 Lab）/ 算法 / 数据 |
| 9 | 旧接口 | 业务后端保留代理，4 周后下线 |
| 10 | run 持久化 | Lab 自己的 MySQL 表，保留 30 天 |

## 三、我基于证据做的判断（不是拍脑袋）

| 判断 | 依据 |
| --- | --- |
| Lab 现在是「挂载」而非「模块」 | `backend/main.py:83` 把 `rc_router` 直接 include 进业务 app，共用 `require_banker` |
| 反馈必须是两段式 | 一次算全量 46 特征在 2 万行上不可忽略；且业务侧常只用 3–5 个指标，全算全传浪费 |
| 输入应以 rows 为主 | Lab 与业务侧对同一份真件的解析结果不一致（569 行无日期 vs 570 行带日期），把解析塞进 Lab 等于把混乱搬过去 |
| 兼容代理必须保留 4 周 | 旧前端 Lab 页 541 行、既有测试与 `parity` 都打旧路径；一天内切完风险不可控 |
| run 必须落库 | 「按 run_id 取数值」隐含 run 可跨请求存在；进程内缓存一重启就没了，演示会当场尴尬 |
| 前端要重组而不是重写 | 标注页 1086 行 + 画布组件 620 行、报告页 1250 行，都已跑通且经过多轮修；重写等于把已验证的功能丢回风险里 |

## 四、仍按假设推进的三条（G8 出口）

1. **端口 8030**：8010/8020/5175 已占，取 8030。若组员发现冲突，改 `LAB_PORT` 即可。
2. **API Key 存 env**：`LAB_API_KEY`，本期不做 Key 轮换与多 Key。需要轮换再说。
3. **自定义特征不迁库**：先把 `var/lab/custom_features.json` 搬到 Lab 自己的目录，避免本周同时动存储与接口。
