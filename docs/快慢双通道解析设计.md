# 快慢双通道解析设计

> 2026-11-07 起实施。灵感来自 intake 的「快慢系统」：实时要快，可靠性靠事后复核。

## 1. 为什么需要两条通道

现在只有一条解析路径：PyMuPDF 主导、解析不到才回退 pdfplumber。这带来两个问题：

| 问题 | 后果 |
| --- | --- |
| 快慢混在一起 | 为了快，把 pdfplumber 当兜底而不是当校验；为了稳，又不敢只用 PyMuPDF |
| 结果没有「被复核过」的标记 | 报告看上去都一样可信，但一份用了 1 秒、一份用了 6 秒，可靠性其实不同 |
| 保险起见只能一直用慢的 | 实时性达标不了 |

快慢分离之后：**快通道负责「马上有结果」，慢通道负责「证明这个结果对」**。

## 2. 两条通道

### 快通道（实时，默认）

- 引擎：PyMuPDF 文字层
- 目标延迟：单份 10 页以内 ≤ 2s
- 产出：完整报告，`verification.status = "pending"`
- 前端标注「结果已出，后台复核中」

### 慢通道（后台，空闲时）

- 引擎：pdfplumber（**不同实现**，不是同一引擎的第二个参数）
- 触发：任务完成即入队；后台线程在本机空闲时逐条处理
- 动作：
  1. 用 pdfplumber 独立重解析同一份文件
  2. 与快通道结果**逐笔对比**
  3. 写回 `verification`
- 结果三态：

| status | 含义 | 前端 |
| --- | --- | --- |
| `passed` | 两条通道逐笔一致 | 「已复核」 |
| `discrepancy` | 有差异，附差异清单 | 「复核发现 N 处差异」，展开可看 |
| `failed` | 慢通道自己跑失败 | 「复核未完成」（不否定快结果，只说明没验证成） |

## 3. 为什么选 pdfplumber 而不是「再跑一遍 PyMuPDF」

同一引擎重跑只能发现随机错误，发现不了**系统性偏差**。
pdfplumber 基于 pdfminer，取词策略、字符宽度、行合并都和 PyMuPDF 不同——
两条路径独立同错的可能性远小于同一路径跑两遍。

## 4. 对比口径

不是比「文本是否一模一样」，而是比**业务字段**：

| 字段 | 比法 |
| --- | --- |
| 笔数 | 必须一致，差 1 笔即 discrepancy |
| 日期 | 逐笔 |
| 金额 | 逐笔，按 Decimal 精确比较（不是 float） |
| 余额 | 逐笔（有则比） |
| 方向 | 逐笔 |

对不齐时按「日期 + 金额」做最长公共子序列，把差异定位到具体笔，而不是只报「不一致」。

## 5. 空闲判定

慢通道不能抢占快通道。判定规则：

- 快通道队列长度 = 0（没有待处理的上传）
- 且距上次快通道任务结束 ≥ 5 秒
- 才处理一条慢任务

这样用户连续上传时复核会自然排在后面，不会拖慢感知到的响应。

## 6. 数据

`report.verification`（JSON，nullable）：

```json
{
  "status": "passed",
  "engine": "pdfplumber",
  "checked_at": "2026-11-07T15:00:00",
  "txn_count_fast": 570,
  "txn_count_slow": 570,
  "diff_count": 0,
  "diffs": []
}
```

## 7. 不做什么

- 不让慢通道**改写**快通道的结果。它只标记、只列差异，不自动修。
  自动修会引入「不知道哪份对」的风险；交给人看差异更安全。
- 不对图片件跑慢通道。图片件两条通道都是 OCR，同错概率高，复核意义小；
  图片件的可靠性靠「置信度 + 用户复核提示」处理。
