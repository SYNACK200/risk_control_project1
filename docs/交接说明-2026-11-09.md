## 一、这个项目到底在做什么

**银行信贷场景的流水真实性核验平台。**

借款人把银行流水（PDF/图片）上传 → 系统解析成逐笔交易 → 核验真实性 + 算 40 项指标 + 出报告 → 银行客户经理据此判断能不能放贷。

三方角色：

| 角色 | 入口 | 干什么 |
| --- | --- | --- |
| 借款人 | `/app/` | 上传自己的流水（本人或代办），看处理进度 |
| 银行员工 | `/bank/` | 看任务列表、报告详情、标注模板、配阈值 |
| 管理员 | `/bank/` 的「系统」组 | 账号管理、审计日志、OCR 路由 |

**核心价值不是"读出流水"，而是"判断这份流水可不可信"。**
所以系统里最重的部分是核验逻辑（真实性五态、四层权重、C1–C10 检查项），不是解析。

## 三、数据流（一条流水的完整生命周期）

```
上传
 └─ FileObj（磁盘文件）+ Task（业务号 T2026...）
     └─ 预读 preread：识别载体（电子/图片/截图）、银行、页数、密码保护、有无文本层
         └─ 选模板：临时模板 > 任务指定模板 > 银行代码匹配
             └─ 解析 parse：三级保底（L1 模板 → L1' 行容差 → L2 通用）
                 └─ 交易入 Txn 表 + Report（快通道，verification.status = "pending"）
                     └─ 慢通道守护线程（快通道空闲 5 秒后）：全量读取，比金额覆盖率
                         └─ 报告 verification 更新为 passed / discrepancy / failed
```

**关键点：报告先出，复核后到。** 不能让用户等慢通道。报告里 `verification.status` 一开始是 `pending`，
慢通道跑完后原地更新。前端要能显示这个"待复核"状态。

## 四、术语词典（这些词会在代码和界面里反复出现）

### 真实性五态

| 值 | 中文 | 含义 |
| --- | --- | --- |
| `pass` | 通过 | 核验项都过了 |
| `grant` | 放行 | 人工开绿灯（白名单），有理由和时间 |
| `supplement` | 需补充 | 材料不全，要补 |
| `fail` | 不通过 | 有硬伤 |
| `unknown` | 无法判定 | 缺条件，不能下结论 |

### 四层权重（真实性得分）

```
content  0.45   内容层：C1–C10 核对（余额链、页合计、笔数…）
ledger   0.30   账务层：借贷平衡、账实相符
file     0.15   载体层：数字对象、字体、图片复用等文件级证据
external 0.10   外部层：外部数据比对
```

载体修正：影像/截图件的载体层证据本身就弱，会降权，降下来的部分按比例回流给内容层和账务层
（它们对影像件仍然可测）。见 `algorithm/algo/verdict.py` 的 `_trust_score`。

得分分级：≥80 `high` 较高 / ≥55 `medium` 一般 / <55 `low` 较低。

### 内容层检查项 C1–C10

| 代号 | 名称 | 看什么 |
| --- | --- | --- |
| C1 | 余额链 | 逐笔递推：本笔余额 = 上笔余额 ± 本笔金额 |
| C2 | 每页合计 | 页脚声明的合计 vs 明细求和 |
| C3 | 笔数 | 页脚声明的笔数 vs 实际行数 |
| C4 | 期初期末 | 文件标的期初/期末余额 vs 明细首尾 |
| C5 | 表头跨页一致 | 多页表头是否一致（版式混装） |
| C6 | 参考号连续性 | 流水号/参考号是否连号 |
| C7 | 时间分布 | 交易时间是否异常集中（凌晨、节假日） |
| C8 | 金额形态 | 金额是否过度规整（整千整万） |
| C9 | 语义匹配 | 摘要与对方是否矛盾（如"工资"但对方是个人） |
| C10 | 重复记录 | 全字段相同的重复行 |

**C1 / C2 / C3 是一票否决项**，见下一节。

### 一票否决（2026-11-07 新增，用户明确要求）

用户原话："一些关键的指标应该是有一票否决权的例如余额连续性或者余额链，其他非关键指标则是有更好。"

`algorithm/algo/content_layer.py`：

```python
CRITICAL_CHECKS = {"C1", "C2", "C3"}
```

判定逻辑（**必须保留成因区分**）：

- 关键项 `fail` 且 `attribution.cause == "data"`（原始数据自身矛盾）→ 内容层直接 `inconsistent`，一票否决
- 关键项 `fail` 但成因是 `recognition`（低置信度行导致断裂，字没认准）→ 只判 `undetermined`，**不当成造假**
- 非关键项 `fail`：`data` 成因仍判 `inconsistent`；识别/版式成因只降为 `undetermined`

**别把这两者合并。** 有测试守着：
`test_low_confidence_break_is_recognition_not_data`、`test_undefined_when_only_low_confidence_rows_break`。

## 五、指标与阈值体系

### 40 项内置指标

`algorithm/algo/metrics.py` 产出。分 A/B/C 等组（覆盖度、收支、负债、异常等），
每项有 `code` / `label` / `group` / `value` / `reason`（算不出来时说明原因）。

### 17 个计算元（atoms）

`algorithm/algo/atoms.py`。纯函数，可组合。自定义指标就是用这些原子拼出来的：

```
评估顺序：过滤 → 分组 → 聚合
evaluate(steps, txns) 按步骤执行
```

### 阈值

`algorithm/algo/thresholds.py` 的 `ThresholdConfig`。

- 内置项 22 个（`dti_high`、`night_ratio`、`net_outflow_ratio` 等）
- **自定义指标阈值**：键名格式 `custom_<指标代号>_max`，存在 `ThresholdConfig.custom` 字典里
  （因为指标代号运行时才知道，不能写成固定字段）
- 超上限产出结论 `CUSTOM_<代号>_HIGH`
- `build_config()` 从库里的 `custom_*_max` 提取进 `custom`；`validate_values` 放行 `custom_` 前缀
- 没设上限就不启用，不误伤

**为什么这条重要**：用户 2026-11-07 说过"不然自定义指标不是完全无效吗"——
自定义指标原先算完只是个数字，不进阈值、不触发结论，等于白算。

### 校验项（识别自检）

`algorithm/algo/verification_defs.py`，38 项。描述每类识别方法（字体分析、数字对象检测等）。

## 六、模板体系（最容易踩坑的部分，重点读）

### layout 结构（当前唯一有效格式）

```json
{
  "page_size": {"w": 595.0, "h": 842.0},
  "page_count": 30,
  "tables": [
    {
      "page": 0,                    // 0-based！界面显示是 1-based，必须转换
      "slot": "first",              // first | middle | last，多页版式不同的处理
      "area": {"x": 0.04, "y": 0.18, "w": 0.85, "h": 0.82},   // 归一化 0-1
      "headerY": 0.197,
      "columns": [
        {"field": "txn_date", "fields": ["txn_date"], "x": 0.318, "w": 0.068}
      ]
    }
  ],
  "pages": {...},   // 旧字段，保留兼容
  "boxes": [...]    // 旧字段，保留兼容，别读它
}
```

**血的教训（2026-11-07）**：`build_layout()` 曾只输出旧的 `boxes`，
而解析器 `table.build_columns` 和前端画布都读 `tables[].columns[]`。
结果：**新建模板的框永远是空的，按框解析从来没生效过**。
所有"模板提速没效果"的观察，根因都是这个。已修，但接手时别读 `boxes`。

### 三级保底

| 级别 | 方法 | 什么时候用 |
| --- | --- | --- |
| L1 | 模板 layout 按框裁剪取词 | 有模板且版式匹配 |
| L1' | 行容差（10pt / 14pt）放宽匹配 | L1 失败，版式轻微偏移 |
| L2 | `parse_generic` 通用解析 | 前两级都失败 |

### 多页版式（slot）

同一家银行不同页码的表格位置可能不同（首页有表头，末页有合计）。

- `tables[].page` 绝对值优先
- `tables[].slot`：`first` / `middle` / `last`
- 边界：1 页 first=last；2 页 second 与 last 同页时用 last；3 页及以上三段独立；中间页沿用 first

### 临时模板（2026-11-07 用户澄清后的正确语义）

**用户原话**："临时标注是给一个临时的调整的模板，因为上传文件的差异性而导致通用模板可能失效，
这时候提供一个临时模板可以尝试进行补救。"
"临时模板不入库，是针对单一份流水的，但是需要注意临时模板是在识别出一份流水文件属于某一个模板
但是上传的流水文件与指定的模板相差太大才需要的。"

要点：

1. **不入库**，只对这一个 Task 生效，用完即弃
2. **触发条件不是用户主动想用**，而是系统先匹配到某个模板、发现实际文件与它差太多
3. 不要做成"用户自己去哪里点临时标注"——那还是让人猜

实现：

- `backend/services/template_mismatch.py`：`detect_mismatch(result, template_used)`
  三个信号：覆盖率 <80%、金额/日期缺失 >20%、余额链断裂 >30%
- 结果写进 `task.check_result.template_mismatch`，报告页显示黄色提示条
- 标注存在 `task.field_map_override`（JSON）

**已知缺陷**：临时模板现在只存字段映射，**没存 layout**，所以重算时还是按表头词中心推算列边界，
不是按用户画的框。要补需给 Task 加一列 `layout_override`。

### 模板删除

**一律软删除**（`deleted_at` + `status="disabled"`），进回收站，可 `POST /templates/{id}/restore` 恢复。

**为什么**：之前"无任务引用"的模板会被**物理删除**，导致 ICBC / CMB / CGB 三个模板被删后无法恢复，
只能重新人工标注。模板是花了人力在样本上画出来的，删错代价很大。

**用户 2026-11-07 明确说过**："模板库里面的模板是我删除的…不要恢复"——
看到模板被删，**不要自作主张恢复**。回收站留着，用户要恢复自己点。

## 七、快慢双通道（用户 2026-11-07 澄清后的正确理解）

用户原话："快通道走的是模板+OCR 模板将原文划分因此可以引入并发读取 但是会面临着模板失效读取错误
慢循环采用全量读取不走模板只提取数进行核验看看有没有问题 paddleOCR可以识别照片"

| | 怎么做 | 强项 | 弱点 |
| --- | --- | --- | --- |
| **快通道** | 模板 + OCR：模板把原文划分成块，再逐块读 | 快 | 模板失效就读错 |
| **慢通道** | 全量读取，不走模板，只提数字核验 | 不受模板影响 | 慢 |

**慢通道不是"换个引擎再解析一遍"。** 它只回答一个问题：
**快通道读出来的那些金额，在原文里能不能找到。**

实现 `backend/services/verify.py`：

- 电子 PDF → pdfplumber 全量抽文字（30 页 8 秒）
- 图片 / 扫描件 → PaddleOCR（它能识别照片，所以图片件也覆盖）
- 只抽金额形态的数字（`_NUM_RE`）
- 判据只有一条：**金额的集合覆盖率**，≥95% 判 `passed`
- 慢通道多出来的数字（页眉账号、余额列、页脚合计）**不算差异**——它本来就该比快通道多
- 逐值计数比对已舍弃：会把 `amount` 与 `balance` 的重复计数当差异，实测 30 页报 316 条假警报

实测建行样例 570 笔：覆盖率 1.0、真差异 0、耗时 8 秒。

### 调度器（慢循环保底）

`backend/services/verify_scheduler.py`，守护线程，20 秒轮询，快通道空闲 5 秒才动手。

**修过的坑**：调度器原本读 `worker._PENDING`，**这个变量根本不存在**，导致 `_fast_busy()` 永远返回 `False`
——慢通道一直和用户上传的任务抢资源。现在读真实计数 `worker.active_count()`。

### 已知未做

**快通道的"模板分区并发"没实现。** 现在只有按框裁剪取词（词数 -32.5%），没有按块并发提交 OCR。
要做需把图片按 layout 的列区域裁开、并发提交、再按坐标拼回，涉及旋转/缩放坐标叠加，风险较高。

## 八、OCR 路由

### 两条路

| 引擎 | 什么时候用 | 凭据 |
| --- | --- | --- |
| 本地 PaddleOCR | 默认，图片少 | 无 |
| 云端 PaddleOCR API | 图片多（≥ min_images），并发快 | API Key + 地址 |

**为什么有云端**：本地 OCR 是 CPU 密集、受 GIL 卡死，线程并行反而更慢。
云端 API 是 HTTP 等待，线程会让出 GIL，并发才成立。

实测（2 张）：串行 17.2s → 并发 2 **8.8s（提速 95%）** → 并发 4 **188.7s 且超时**（服务端限流）。
**默认并发定为 2，别凭直觉改成 8。**

### 配置项（`ocr_routing` 表，单行）

```
enabled      开关
min_images   图片数门槛（≥ 才走云端）
workers      并发路数（默认 2）
model        模型名（默认 PP-OCRv6）
endpoint     API 地址（留空用默认 aistudio 域名）
api_key      API Key
```

**凭据优先级**：界面配置 > 环境变量 `PADDLEOCR_ACCESS_TOKEN` > `~/.dsh/ocr/paddle.json`

安全约定：

- 接口只返回 `has_api_key`（布尔），**永远不回显明文**
- 保存时 `api_key` 留空表示"不改"，避免误清已存的值
- 日志不打印 key
- 关闭云端路由时，前端**隐藏**地址与 Key 字段（用户明确要求：关掉时不该看到这些）

### 端点坑

正确端点是 `/api/v2/ocr/jobs`（异步任务制：提交拿 jobId → 轮询 → resultUrl → 下载）。
`~/.dsh/ocr/paddle.json` 里的 `endpoint` 字段是 **v1 域名，直接用会 404**。

### 已知未接入

`should_use_api(db, image_count)` 已写好，但 `task_runner` 的多文件分支**还没接线**。
即：路由配置生效了，但主解析链路还没真的按它分流。

## 十二、踩过的坑（别重犯，这些都是真金白银的教训）

### 前端 / CSS

**改 `app.css` 后必须校验花括号平衡。** 已经踩过两次，一次是 `.trust-chip` 少个 `}`，
把之后所有规则都吞了（`.inline-field`、`.infer-preview` 全失效，预览格子显示成一串数字）。

```bash
node -e "const c=require('fs').readFileSync('src/styles/app.css','utf8');
const o=(c.match(/{/g)||[]).length,cl=(c.match(/}/g)||[]).length;
console.log(o===cl?'OK '+o:'不平衡 '+o+'/'+cl)"
```

**验收必须带 `?nocache=<ts>`。** 否则加载的是旧 bundle，会误判"修了但没生效"。
PDF 中文不渲染那次就是被我误判成"未修"，其实是浏览器缓存。

**`Annotate.tsx` 有 1100 行，插入多行 JSX 极易破坏结构**（历史失败 5+ 次）。
安全做法：抽独立组件 + 单行替换。`ColumnFieldList.tsx` 就是这么抽出来的。

**CSS 选择器优先级**：`input[type=number]`（0,1,1）会压过 `.thr-input`（0,1,0）。
阈值输入框显示成 `0` 只露第一位就是这个原因，要写成 `table.thr-table input.thr-input`。

### 事件拦截（2026-11-07 最新教训）

**改 pointerdown 拦截逻辑时，必须把四种操作各走一遍**：选中 / 拖动 / 改大小 / 画新对象。

为修"加不上新列"加了 `if (p.tool === 'column') return`，结果把所有模式都放行了，
表格区和列**根本点不中** → 出不了八个手柄 → 改不了大小。
修法是新增 `select` 工具类型并设为默认，只有 `select` 模式响应选中/拖动。

### 后端 / 算法

**`from datetime import ...` 不能写在函数中部。** Python 会视其为局部变量，
首次使用报 `UnboundLocalError`。`update_template` 曾因此保存新版本失败。

**layout 读 `boxes` 是错的**，读 `tables[].columns[]`。见第六节。

**页号 0-based / 1-based 转换**：layout 存 0-based，界面显示 1-based。
`TemplateLayoutPage` 载入时转 1-based、保存时转回 0-based。
不转的话 `t.filter(t => t.page === page)` 会全滤掉，框一个都不渲染。

**`page.get_text` 线程并行无效**。实测：单独 +35%，但包进 `_fitz_page_words` 后整体 1.06s→2.03s；
`find_header` 1.06s→2.44s（负收益）。根因是 GIL。`ProcessPoolExecutor` 在 uvicorn 内会
`BrokenProcessPool`（Windows 需 `__main__`）。**真实提速来自按框裁剪取词（词数 -32.5%），不是并行。**

### 环境 / 运维

**`taskkill /F /IM chrome.exe` 会关掉用户所有浏览器。** 只杀带 `cdp-profile` 的实例：

```bash
wmic process where "name='chrome.exe' and commandline like '%cdp-profile%'" get processid
```

CDP 验收：`chrome.exe --remote-debugging-port=9222 --user-data-dir=E:/TMP/cdp-profile --headless=new`
上传文件用 `DOM.setFileInputFiles`（headless 点不开文件选择器）。

**日志是 UTF-16**，grep 前先 `tr -d '\000'`。

**Git Bash 的 `python` 模板字符串里嵌 Python 代码容易解析失败**，
复杂改写用独立 `.py` 文件 + `io.open` 读写，别在 `run_code` 里拼长字符串。

## 十三、工作约定（用户明确要求，必须遵守）

### 汇报格式（2026-11-07 要求）

汇报"发现的问题"用三段式，**前导词只是文段标识、紧接着正文，读起来是一段白话**：

```
问题：功能上/结果上发生了什么，用户视角、能看懂
解决状态：已修 / 未修 + 现在卡在谁那里
事后反馈：会怎样、不会怎样 + 用户能从哪儿进一步改进或决策
```

**不要用方括号**（`[问题]` 会被界面渲染成链接）、不加粗、不单独占一行、不套列表符号。
同一个大点下有多个小点（①②③）时，**小点之间空一行**。

技术细节（路径、函数名、行号）只放文件报告正文，对话里只留一个够用的数字。

### 报四件事

每次交付必须说清：**做了什么 / 没做什么 / 没验证什么 / 有什么风险。**

### 版本语义

`CHANGELOG.md` 是**唯一权威**，tag 只是锚点，不逐条对应提交。
当前最新 tag `v0.40.0`，之后 25 个提交都在"未发布"段里。

### Git（G4 规则）

- 任务 → 分支；本地常驻 `main` + `dev`
- 里程碑打 tag
- 远端：GitHub `origin`（`SYNACK200/risk_control_project1`）、Gitee `gitee`（`jackzhang83/cashflowanalysis`）
- Gitee 主分支叫 `master`（对应本地 `main`），推送用 `main:master`
- **Gitee token 必须用 `https://oauth2:TOKEN@`**，用 `https://用户名:TOKEN@` 会 403
  （`token username invalid`）。用临时 URL 推，推完不用清理 remote

### 用户偏好

- 先讨论后动手，不自作主张
- 证据优先，不凭感觉
- **用户说"不要 push"就不要 push**；说"推到仓库"再推
- **不要恢复用户删掉的东西**（模板被删是用户的决定）
