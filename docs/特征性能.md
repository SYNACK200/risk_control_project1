# 特征性能与边界（AL-106）

> 目的：给「2 万行能不能算、慢在哪、边界会不会静默出错」一个可复查的答案。
> 工具：`python -m rc_platform.tools.feature_bench --rows N`；只跑 46 个内置特征的纯计算，不含解析、不读写数据库。
> 环境：Windows / Python 3.12 / 单进程 / 本机 venv；金额全 Decimal。

## 一、耗时与内存

本机两次独立测量（中间修过 `f_month_in_cv`、`f_large_out_share`、`within_days`），耗时波动 2–3 倍，**说明本机负载/降频影响很大**，但结论不变：2 万行全量不能同步跑。

| 行数 | 46 特征总耗时（第一次 / 第二次） | 峰值内存 |
| --- | --- | --- |
| 0 | 9.1 ms | 0.1 MiB |
| 1 | 13.5 ms | 0.1 MiB |
| 1,000 | 1,196.4 ms | 0.4 MiB |
| 5,000 | 6,850.5 / 16,633.1 ms | 1.5 MiB |
| 20,000 | 41,513.9 / 131,003.3 ms | 5.6 MiB |

**内存不是瓶颈（20k 峰值 5.6 MiB）；瓶颈是 CPU。** 即使按最好的 41.5 秒，也不适合放进同步接口。

## 二、单特征超过 200ms 的项（20,000 行，第二次测量）

| 特征 | 耗时 | 原因判断 |
| --- | --- | --- |
| `f_night_large_out_count` | 59,919.2 ms | `pct_rank()` 写在 `count(where=...)` 里，疑似逐行重算全表分位，复杂度接近 O(n²)。1k→5k→20k 从 56ms → 3.2s → 60s，增长明显超线性。 |
| `f_large_out_share` | 1,217.9 ms | 加了「没有大额出账返回 0」的 guard 后，多了一次 `count` 全表扫描；两次扫描 + 逐行条件。 |
| `f_night_out_share` | 832.2 ms | 两次全表扫描（夜间出账额、全部出账额）叠加逐行条件。 |
| `f_month_in_cv` | 788.2 ms | 改成补空月 + 总体标准差后，表达式里 `monthly_values` 被调用 3 次，每次全表分组。 |
| `f_cash_out_share` | 674.1 ms | 两次全表扫描 + `in_lexicon` 逐行匹配。 |
| `f_round_amount_share` | 673.6 ms | 逐行做 Decimal 取整/比较。 |
| `f_in_out_ratio` | 642.1 ms | 两次全表求和。 |
| `f_debt_service_ratio` | 620.1 ms | 多个 `in_lexicon` 条件分别扫全表。 |
| `f_weekend_out_share` | 609.7 ms | 两次全表扫描 + 星期判断。 |
| `f_weekend_out_total` | 558.2 ms | 逐行星期判断 + 求和。 |
| `f_online_loan_out_share` | 517.5 ms | `in_lexicon` 逐行匹配 + 两次求和。 |
| `f_net_flow` | 516.5 ms | 两次全表求和。 |
| `f_salary_in_share` | 515.3 ms | `in_lexicon` 逐行匹配 + 两次求和。 |
| `f_night_count` | 391.2 ms | 逐行时间解析 + 条件判断。 |
| `f_robust_outlier_count` | 386.8 ms | 中位数/MAD 需要排序后再扫一遍。 |
| `f_out_median` / `f_out_cv` / `f_out_std` | 259–267 ms | 排序或两遍统计。 |
| `f_in_mean` / `f_in_cv` / `f_out_mean` / `f_in_total` / `f_out_max` / `f_out_total` | 200–237 ms | 单次全表扫描，接近 200ms 线。 |

**优先修 `f_night_large_out_count`**：把 `pct_rank()` 提到 `where` 外面先算一次序列，或在 `Frame` 上缓存分位数组；目标是 20k 行降到 200ms 以内。其次把 `f_month_in_cv` 的三次 `monthly_values` 合并成一次，把同类「两次全表扫描」的特征改成一次遍历。

## 三、边界行为

| 输入 | 行为 | 原因码 |
| --- | --- | --- |
| 0 行 | `f_txn_count` 返回真正的 0；其余依赖数据的特征返回 null | `no_rows`（明细为空） |
| 1 行 | 不崩溃；标准差/变异系数/斜率等返回 null | `insufficient_period`（少于 2 笔/期数不足） |
| 金额为负 | 当前不拦，按原值计入（`direction=out, amount=-100` → `f_out_total=-100`），不会被悄悄改成 0 | 无（值可算） |
| 余额列整列为空 | 余额类特征返回 null | `missing_column` |
| 交易时间列整列为空 | 夜间类特征返回 null | `missing_column` |
| 对手方列整列为空 | 集中度/前三特征返回 null | `missing_column` |
| 过滤后无数据 | 返回 null，不报 0 | `no_rows`（按条件过滤后没有可聚合的数据） |

金额为负这一条**是当前事实，不是推荐口径**：如果上游确认负金额应视为非法输入，应在 `parse_statement` 或特征入口统一拦成 `invalid_input`，而不是让 `f_out_total` 出现负数。

## 四、验收口径

- 本次记录的是 20,000 行、46 特征、单进程的实测值；换机器或换 Python 版本要重跑。
- 「单特征 >200ms 要标出来」已满足；`f_night_large_out_count` 是唯一需要先修的性能缺陷。
- 边界测试在 `rc_platform/capabilities/features/tests/test_bounds.py`，覆盖 0 行、1 行、负金额、三类缺列。
- 原因码字典与 AL-105 共用，见 `rc_platform/capabilities/features/defs.py` 的 `REASON_CODES`。
