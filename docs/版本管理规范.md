# 版本管理规范

> 2026-10-31 起执行。此前 37 个标签（v2.0.0 – v6.4.3）全部收回，见 [版本历史归档-2026-10.md](./版本历史归档-2026-10.md)。

## 1. 为什么重来

| 问题 | 现象 |
| --- | --- |
| 大版本滥用 | 两天内从 v2.0.0 跳到 v6.4.3，每次新功能都抬 major |
| 时序错乱 | v2.7.0 / v2.8.0 是在 v3.0.0、v4.x 之后才补打的标签，标签顺序与提交顺序不一致 |
| 重复主题 | 多账户合并先后出现在 v2.7.0、v4.0.0、v4.1.0 |
| 含义丢失 | 大量 PATCH（v6.1.1/.2/.3）其实是新功能，语义不成立 |

## 2. 现在的规则

版本号：`vMAJOR.MINOR.PATCH`（项目尚未对外发布，MAJOR 保持 0）

| 位 | 什么时候 +1 | 例子 |
| --- | --- | --- |
| MAJOR | 对外发布 / 不兼容变更（数据结构、接口契约破坏） | 正式交付时 `v1.0.0` |
| MINOR | 新增一项可独立验收的能力 | 新增“账号体系”→ `v0.3.0` |
| PATCH | 只改缺陷或文案，不改能力边界 | 修“模板删不掉”→ `v0.4.1` |

### 打标签的硬条件

1. `dev` 与 `main` 已对齐且 CI 测试通过（algorithm + backend + 两侧构建）。
2. 标签**必须**是 annotated tag，注释里写清“这一版能做什么”。
3. **一个里程碑一个标签**：同一天多个小修只累计，不连续打 PATCH。
4. 标签一旦推送不改写；确需改名按“删除 + 重建 + 归档说明”走。
5. 归档：每次收回标签必须在 `docs/` 留映射表（旧名 → 提交 → 新名）。

## 3.1 2026-11-07 的收编（第二次犯同样的错）

11-07 一天打了 10 个标签（v0.30.0 – v0.39.0），其中 3 个是纯文档提交，违反了第 2.3 条。
已按第 2.5 条收编进 v0.40.0，映射表见 [版本历史归档-2026-11.md](./版本历史归档-2026-11.md)。

复发的根因：把「提交」当成了「版本」。以后判断标准只有一条 ——
**这个标签对应的状态，能不能拿去给别人演示 / 交付？** 不能就不是里程碑。

本次新增两条硬约束：

6. **纯文档提交不打标签**，进 CHANGELOG 的「未发布」即可。
7. **一天最多一个标签**；同一天再有改动，追加提交，等下一个里程碑一起标。
