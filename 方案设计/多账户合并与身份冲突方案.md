# 多账户合并与身份冲突方案

> 版本 v1（2026-10-30）。一句话：**账户像分支，户名像提交者；同一人的多个账户可以合并成一份画像，同一账户挂多个户名就是冲突，必须告警。**

## 1. 为什么需要

| 现实情况 | 系统要做什么 |
| --- | --- |
| 一个客户在多家银行、多个账户有流水 | 合并成一个客户的整体风险，而不是分开看 |
| 客户可能借用他人账户、或用同一账户提交不同户名（绕过单账户额度/风控） | 识别「一个账户多个户名」，给出高风险告警 |
| 多份流水时间区间重叠 | 合并时不能把重叠月份算两次（double counting） |

## 2. 概念映射（借鉴版本控制）

| Git | 本系统 |
| --- | --- |
| 分支 branch | 一个银行账户（银行 + 账号） |
| 提交者 author | 户名（账户持有人） |
| 合并 merge | 把同一户名下的多个账户汇总成一份风险画像 |
| 冲突 conflict | 同一账户出现多个户名，或同一户名指向互相矛盾的账户 |
| 合并策略 | 加总 / 并集去重 / 独立假设 / 取最大 / 等权 / 余额加权 / 尾部合并 |

## 3. 实体识别

数据来源：每个任务的预读结果（`task.check_result.preread`）——银行名、脱敏账号、脱敏户名、期间。

| 关联强度 | 依据 | 处理 |
| --- | --- | --- |
| 强 | 同一银行 + 同一账号 + 同一户名 | 直接合并 |
| 中 | 同一户名 + 不同账号 | 可合并，但标注「跨账户」 |
| 弱 | 户名未识别 | 单独成组，合并结果标注可信度低，必须人工核对 |

当前只使用脱敏后的户名与账号（预读阶段就脱敏），因此**同名不同人**可能被误并；这是已知限制，见第 8 节。

## 4. 冲突告警（越狱检测）

| 规则 | 触发条件 | 等级 | 提示 |
| --- | --- | --- | --- |
| `account_multi_holder` | 同一（银行+账号）出现 ≥2 个不同户名 | 高 | 疑似借用账户、冒用他人流水或代持 |
| 待补 | 同一户名在极短时间内出现在不同城市的网点 | 中 | 需接入网点/设备信息 |
| 待补 | 同一账号反复出现在不同客户的授信申请 | 高 | 需接入申请主数据 |

处置建议（给审批人）：先核对身份证件与授权书；冲突未澄清前，该账户的流水不得作为授信依据，只能作为风险信号。

## 5. 七种合并方式（实现取自 algorithm/algo/merge.py）

合并分两层：**流水层**处理「钱」（去重、抵消内部转账、按期间并集），**指标层**处理「分」（木桶/凸性/加权/证据）。页面只显示一句人话，点「这个方式怎么算？」才展开公式与偏差。

| 名称 | 公式 | 什么时候用 | 已知偏差 |
| --- | --- | --- | --- |
| 合并并抵消内部转账（推荐） | 合并 = Σ明细 − 重复指纹 − 内部转账成对记录 | 多账户且账户之间可能互转 | 依赖同日或相邻日、金额相等；跨行延迟超 2 天会漏判 |
| 直接相加 | 合并 = Σ 各账户明细 | 只想看规模、账户间无互转 | 互转记两次，收入与支出都虚高 |
| 仅去重后相加 | 合并 = Σ明细 − 重复指纹 | 同一份流水被重复上传 | 不处理互转 |
| 最坏情形（木桶） | 取各账户同一指标的最差值 | 关心短板，不看平均 | 偏悲观，不能用于额度测算 |
| 凸性聚合（惩罚集中） | 对集中度类指标做非线性放大 | 账户体量差异大、警惕集中 | 需要先校准放大系数 |
| 按规模加权平均 | Σwᵢxᵢ，wᵢ≥0，Σwᵢ=1 | 账户体量差异大、做稳健估计 | 不反映总额 |
| 证据合成（真实性） | 按各账户的真实性等级给权重再合成 | 各账户流水可信度不同 | 权重依赖核验结论 |

重叠期间：引擎按各账户期间取并集，重叠不重复计数（不再由用户单独选择重叠算法）。

理论依据：Artzner et al. (1999) 一致性风险度量（次可加性、正齐次性）；Basel IRB 的集中度与相关性假设。
**本地联网检索不可用，以上为教科书结论，未逐条核对原文。**

## 6. 指标合并策略（重要）

| 类型 | 指标 | 做法 |
| --- | --- | --- |
| 可加分量 | A01 收入、B01 还款、C01 净流入 | 按所选方法合并 |
| 比率类 | A02 月均、B02 DTI、C02 流入流出比 | **不直接相加**，按合并后的分子/分母重算 |
| 余额类 | C03 日均余额、C04 波动率 | **不合并**：同一时点同一笔钱只在一个账户 |
| 需明细重算 | A03 中位数、A04 稳定性、A05 工资占比、B04 平台数、E01 集中度 | 当前不提供，页面明确写出原因 |

## 7. 风险等级合并

单账户风险命中数 = 该账户报告里命中阈值结论的条数；合并后按方法折算（加总求和后封顶 3、取最大取最大、独立按平方和开根、加权按权重），再映射 高/中/低/未见。

## 8. 已知限制

| # | 限制 | 影响 |
| --- | --- | --- |
| 1 | 只用脱敏户名做关联，未接实名/身份证 | 同名不同人可能误并 |
| 2 | 预读的账号可能缺失 | 缺失时账户键退化为 UNK，合并可信度下降 |
| 3 | 实体关系不落库（按任务实时聚合） | 数据量大时需建 account/subject 表与索引 |
| 4 | 未识别「同一人不同证件类型」 | 需接入证件主数据 |
| 5 | 余额类指标不做合并 | 客户整体资产负债需另建口径 |

## 10. 超可加：同步流水不能简单相加

> 评价体系不一定是线性的：两笔在时间上同步的流水，合起来的风险可能大于各自之和。
> 这不是「按凸组合给分数加权」，而是合并规则本身允许超可加（superadditive）。

### 为什么
- 两个账户在同一个月同时大额流出（例如同时抽贷、同时转给同一收款人），对还款能力的冲击大于两笔流水各自风险的算术和；
- 流动性、集中度、多头借贷这类风险度量，本身就可能在同步事件下放大。

### 规则（merge.py 的 sync_amplify）
1. 按账户、按月汇总流入/流出；
2. 某账户当月流出 ≥ 其月均流出的 80%，或当月净流出 < 0，记为「压力」；
3. 同一月份 ≥2 个账户压力 → 记为同步月；
4. 同步率 = 同步月数 / 总月数；λ 默认 0.5（环境变量 MERGE_SYNC_LAMBDA 可调）；
5. 风险型指标：M = Σ mᵢ × (1 + λ·同步率)，系数 > 1 即超可加；
6. 没有同步月时系数 = 1，退化为普通相加（不会无端放大）。

### 实测
| 场景 | 同步月 | 系数 | 指标 C05 |
| --- | --- | --- | --- |
| 王五两个账户，4/5 月各转出 4800（≥ 月均 80%） | 2 / 2 | ×1.5 | 200 → 600 |
| 两个账户月份不重叠 | 0 | ×1.0 | 等于相加 |

### 与「凸性聚合」的区别
| 模式 | 做什么 | 不是做什么 |
| --- | --- | --- |
| 凸性聚合 convex | 惩罚集中度 √(Σ mᵢ²) | 不处理同步事件 |
| 同步放大 sync_amplify | 同步压力下放大风险（超可加） | 不是给分数做凸组合加权 |

### 边界
1. 月份粒度；同月不同日也算同步（更保守）。
2. λ 是业务参数，需按样本校准；当前 0.5 为暂定。
3. 放大只作用于 SYNC_AMPLIFY_CODES（风险型指标），金额类指标仍按并集重算。
4. 同步判定依赖「月均流出 80%」这条线，对收入波动大的客户可能误判。

## 11. 口径按「业务问题」重写（v6.2.2）

> 之前 8 个口径是数学描述（`凸性聚合`、`证据合成`、`最坏情形木桶`），银行人员看不懂。
> 现在每个口径都用「回答什么问题 + 会怎么做 + 对结论的影响」来表达，并分为常用 3 个、特殊 5 个。

### 常用（默认可见）

| 口径 | 回答的问题 | 对结论的影响 |
| --- | --- | --- |
| **真实收支（推荐）** | 这个客户自己到底赚了多少、花了多少？ | 剔除本人账户互转，收入与支出都低于直接相加 |
| **授信从严（按最差账户）** | 如果他最差的账户就是真实状态，最多能承受多少？ | 比看平均值保守，风险等级可能更高 |
| **流水总量（不做调整）** | 这些流水加起来一共有多大？ | 互转被重复计算，收入支出偏高，不能算 DTI |

### 特殊情况（折叠）

| 口径 | 回答的问题 |
| --- | --- |
| 去重后总量 | 这些材料里有没有重复提交的同一笔流水？ |
| 按主要账户（加权） | 能不能以工资主账户为主、其它账户只作补充？ |
| 风险集中度 | 风险是不是压在单一账户上？ |
| 材料互证（真实性） | 这几份材料之间能不能互相印证？ |
| 多账户同步压力 | 他是不是在同一时间从多个账户一起抽走大额资金？ |

### 接口变化

`/entities/methods` 每项新增 `question`（业务问题）、`approach`（会怎么做）、`impact`（对结论的影响）、`when_to_use`（什么时候选它）、`tier`（primary/advanced）；旧的 `short/detail/formula/assumption` 保留，报告页仍在用。

## 12. 合并页并入「客户与账户」+ 多对象合并（v6.3.0）

### 12.1 为什么要合并

「客户与账户」和「账户合并」原本是两个 tab，做的是同一件事：同名多账户 → 合并成一份画像。分成两个 tab 会让工作人员不知道该点哪个。现在只保留「客户与账户」，合并能力全部在里面。

### 12.2 多个怀疑对象

同名多账户的客户往往不止一个，所以：

| 能力 | 说明 |
| --- | --- |
| 建议列表 | 一次列出全部「同名 ≥2 账户」的怀疑对象，每张卡片可勾选 |
| 批量合并 | 「合并选中的 N 个」或「合并全部建议（N 个）」，逐个按当前口径计算 |
| 结果切换 | 合并后出现结果标签条（户名 · 风险等级），点哪个看哪个的明细 |
| 单独查看 | 单张卡片的「只看这一个」 |

### 12.3 实测

| 项 | 结果 |
| --- | --- |

| 建议卡 | 2 个（王* 2 账户、张* 2 账户） |
| 批量按钮 | 「合并全部建议（2 个）」 |

| 切换 | 点「张*」后高亮切换，明细仍在（5 个指标分组） |
