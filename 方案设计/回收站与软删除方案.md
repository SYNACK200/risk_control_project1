# 回收站与软删除方案

> 一句话：**列表只增不减会淹没真问题；移入回收站是「不显示、不参与、可恢复」，彻底删除才真的删。**

## 1. 为什么不是直接删

| 直接删的风险 | 本方案 |
| --- | --- |
| 误删无法挽回（明细、报告、指标全没） | 软删除只打 `deleted_at`，数据全在 |
| 审计要求「删除」也要留痕 | 每次回收/恢复/彻底删除都写 `audit_log` |
| 已出报告可能用于复核 | 回收站里的任务仍可按 ID 打开报告 |

## 2. 数据模型

| 字段 | 说明 |
| --- | --- |
| `task.deleted_at` | 为空 = 在用；非空 = 在回收站（时间戳） |
| 迁移 | `db/migrate.py::ensure_columns()` 幂等补列，启动时执行 |

## 3. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/tasks?trash=1` | 回收站列表（默认只返回在用） |
| POST | `/tasks/recycle` | 批量移入回收站，body `{task_ids: [...]}` |
| POST | `/tasks/restore` | 批量恢复 |
| POST | `/tasks/purge` | **彻底删除**，必须 `confirm=true`，且只能删回收站里的 |

彻底删除的级联范围：`txn`、`metric_value`、`report`、`task_file`、`bank_account`、`task`。
材料文件（`file_obj`）不删，因为可能被其它任务共用（同一份材料多任务引用）。

## 4. 页面行为

1. 列表头「流水列表 / 回收站」两个视图，各自保留筛选条件。
2. 每行复选框 + 表头全选；选中后出现批量条：`已选 N 条` + 动作按钮。
3. 动作走**页内两步确认**（不用系统弹窗）：`移入回收站` → `确定…？[确认][再想想]`。
4. 回收站里每行同样可勾选，动作变为 `恢复` / `彻底删除`。
5. 操作完成提示条：`移入回收站完成：2 条`。

## 5. 关键决策

| 决策 | 理由 |
| --- | --- |
| 用 `deleted_at` 而不是 `status=ARCHIVED` | 与状态机解耦：状态机管流转，回收站管可见性 |
| 默认列表过滤回收站 | 银行看流水默认不应看到已清理的 |
| 彻底删除必须二次确认 + 只允许回收站内 | 防误删在用流水 |
| 回收站里的任务仍可按 ID 看报告 | 复核需要 |
| 实体/合并页只看在用 | 已清理的流水不应再进客户画像 |

## 6. 实测

| 操作 | 结果 |
| --- | --- |
| API：回收 2 条 | 在用 14→12，回收站 2 |
| API：恢复 1 条 | 在用 13，回收站 1 |
| API：purge 未带 confirm | 400 拒绝 |
| API：purge 带 confirm | 删除 1 条，级联清理明细/指标/报告 |
| 页面：勾 2 条 → 移入回收站 | 共 12→10，提示「完成：2 条」 |
| 页面：回收站视图 | 共 3 条 |
| 页面：恢复 1 条 | 回收站 3→2 |
| 页面：彻底删除 1 条 | 回收站 2→1 |

## 7. 边界

| # | 边界 | 说明 |
| --- | --- | --- |
| 1 | 回收站没有自动清理策略 | 可选：30 天后自动彻底删除（需定时任务） |
| 2 | 彻底删除不删 `file_obj` | 避免误删共享材料；**磁盘不会因此释放**，若要释放需单独做孤儿文件回收 |
| 3 | 回收站不按时间排序筛选 | 目前按 id desc；要「最近删除」可加 `order=deleted_at` |
| 4 | 没有撤销（Undo） | 恢复入口就是回收站 |
