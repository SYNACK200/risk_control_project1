# 任务队列与并发方案（v0.5.0）

> 目标：把「解析 + 核验 + 指标 + 报告 + 落库」从请求线程挪到后台进程池，请求立刻返回 QUEUED，前端轮询进度。

## 1. 之前是什么样

| 问题 | 现象 |
| --- | --- |
| 同步执行 | 上传接口声明 202，实际在请求里跑完分析才返回（响应里 status 已是 DONE） |
| 单进程 | uvicorn 单 worker，CPU 密集解析受 GIL 限制，实测 8 并发 = 8× 单份耗时 |
| 无排队状态 | 多人同时上传只能干等，界面看不到「排队中」 |

## 2. 现在的结构

```
POST /tasks ──► 保存文件、第 1 页预读、模板匹配
             └─► 建 Task(status=QUEUED) ──► worker.submit_task()
                                              │
                    ProcessPoolExecutor(2) ───┴──► task_runner.run_task(task_id)
                                                    ├─ 自建 DB 连接（子进程内 init_db）
                                                    ├─ CHECKING→PARSING→VERIFYING→REPORTING→DONE
                                                    └─ 失败 → FAILED + 审计原因

GET /tasks/{id} ◄── 前端每秒轮询（借款侧进度页已有轮询，银行侧列表刷新）
```

| 组件 | 文件 | 职责 |
| --- | --- | --- |
| 进程池 | `backend/services/worker.py` | 提交、预热、崩溃兜底置 FAILED、优雅关闭 |
| 执行器 | `backend/services/task_runner.py` | 一次完整分析的领域流程（可独立在子进程运行） |
| 状态机 | `backend/services/workflow.py` | 新增 `QUEUED`：PENDING→QUEUED→CHECKING→…；DONE→QUEUED 支持重算 |

## 3. 配置

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `ANALYSIS_BACKEND` | `process` | `process`=进程池；`inline`=同步执行（测试/调试） |
| `ANALYSIS_WORKERS` | `2` | 进程数，建议 ≤ CPU 核数 |

## 4. 实测（8010，acct_a 小样本）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 单份上传响应 | 255 ms（响应即 DONE） | ~250-390 ms（响应即 QUEUED，分析在后台） |
| 单份端到端 | 255 ms | ~750 ms（含排队与进程调度） |
| 4 并发总耗时 | 1020 ms（串行） | 1786 ms（提交 1394 + 分析 392） |
| 8 并发总耗时 | 2070 ms（串行） | 2664 ms（提交 2019 + 分析 645） |
| 8 并发失败 | — | 0（修复死锁后） |

**怎么看这组数字**：

- **用户感知变好**：请求立刻返回，不再等分析；进度页能看到「排队中 → 解析中 → 完成」。
- **总吞吐对"小文件"没变好**：请求里还保留第 1 页预读（判断是不是流水、匹配模板），它仍在父进程里被 GIL 串行；小文件的分析只占 250ms 中的一小部分。
- **分析阶段已经真并行**：8 份的分析阶段 645ms，而串行会是 ~2s。文件越大收益越明显（59MB 件单份 2.2s）。

## 5. 已知限制

| # | 限制 | 后续 |
| --- | --- | --- |
| 1 | 请求内仍做第 1 页预读，8 并发提交耗时随份数线性增长 | 把预读也挪进 worker（拒绝改为异步，前端提示「材料不符合要求」） |
| 2 | 并发上限=进程数，超出排队但队列长度不可见 | 加队列长度与预计等待时间 |
| 3 | 无失败重试 | 进程崩溃已兜底置 FAILED；可加自动重试 1 次 |
| 4 | 子进程首次调用会加载算法依赖（预热已缓解） | 预热改为启动时等待完成（会延长启动 ~10s，故未开） |
| 5 | 密码随任务参数传给子进程（进程内内存，不落库） | 可改为临时解密后传文件路径 |

## 6. 死锁修复

并发写 `metric_value` 时触发 MySQL `1213 Deadlock`（间隙锁）。处理：

1. 子进程会话设 `READ COMMITTED`，减少间隙锁；
2. 落库提交加 3 次退避重试（仅对 1213/Deadlock）。
